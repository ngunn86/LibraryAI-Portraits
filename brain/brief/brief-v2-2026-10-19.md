# The portraits tool: a brief to start from (second edition, 2026-10-19)

For the chat that plans and builds the portraits tool. The tool is a standalone app in its own repo, and it is also the first project the autonomous build harness runs end to end (Library-AI's readiness gate G10). It is built before the library exists, so nothing in it may depend on the library running: it takes a list of teachers the owner supplies, finds and makes the portraits, and delivers files and metadata to a Google Drive folder the owner shares; the library's build later reads that folder. The full requirements are the `tool`-tagged lines in `brain/spec/portraits.md` of the Library-AI---Rev1 repo (PORT-001 to PORT-022, PORT-040, PORT-070 to PORT-081, PORT-091); the hand-off contract is `brain/contracts/portraits.manifest.schema.json` with its sample. Attach those three files to the chat with this brief.

What changed since the first edition (2026-10-17): the tool no longer reads teachers or requests from the library's API, and no longer posts portraits to it. Its input is a teacher list file; its output is a Drive folder. The library's side (the Drive door that reads the folder, the queue item, the people screen, the credits page) is the library's build and is listed at the end so the two projects agree.

## What it does

For every teacher on the list who has no approved portrait, find a public-domain or openly licensed photograph that certainly shows them, make a stylized portrait in the owner's halftone style, check it, and deliver it with its rights record to the Drive folder, where the library will pick it up and an admin will approve it. The owner's three hand-made portraits in `design/portraits/` are the target; the tool's job is to match them, by code, for a few hundred teachers.

## Inputs

1. **The teacher list, `teachers.csv`** (the owner supplies it; the library's people records don't exist yet). One row per teacher, UTF-8, with a header:
   - `teacher_id`: a stable slug the owner chooses (`charles-fillmore`), which the library will adopt as the person's id or alias, so every file and record can be matched later without a lookup;
   - `name`: the name as the library will show it;
   - `born`, `died`: years, or fuller ISO dates where known; blank when unknown (the tool then treats a match as uncertain and needs an authority id);
   - `wikidata_qid`: optional, `Q…`, which makes matching certain;
   - `aliases`: optional, other names and spellings, separated by ` | `;
   - `notes`: optional, free text for the owner (a movement, a hint such as "photo in the 1912 yearbook"), never used for matching.
   A teacher whose row has neither a Wikidata id nor both years can still be searched, but only an authority match (below) counts.
2. **Requests, `requests.json`** (later runs; absent on the first): written by the library into the same Drive folder when an admin asks for Try again with a note, Find another original, or a pasted Commons or Library of Congress link to try (PORT-060, PORT-061). Each request has an `id`, the `teacher_id`, the kind, the note and the link if any. A run takes requests first, then teachers without a portrait, and skips teachers the library has marked approved (the library also writes `status.json`: each teacher's portrait status, which the tool reads when present and otherwise assumes nothing is approved).
3. **The owner's three examples** (`design/portraits/`), the targets for the style and the trial.
4. **The settings file:** the recipe settings, the three model names, the spend cap, the Drive folder's id, the paths of the list and the examples. Keys (OpenRouter, a fal key if needed, the Drive credential) live outside the repo, never in it or in chat.

## Where originals come from (fixed; rights)

- Wikimedia Commons and the Library of Congress only. Public domain first (public domain, CC0, the Library of Congress's "no known restrictions"), then CC BY and CC BY-SA; nothing else, ever (no NC, ND, fair use or unknown rights). Never the library's own scans or the owner's reference shelf.
- A certain match only, in this order: the image on the teacher's Wikidata record (P18); Commons files whose structured data says they depict the teacher's Wikidata item (P180); Library of Congress prints and photographs whose record names the teacher with matching dates. A file merely in a Commons category, or matched by name alone, never counts. A pasted link in a request is taken as the owner's own match and recorded as such.
- Every original's record is kept: source, source id, page and file links, title, author and date as given, licence and its link, credit line, how it was matched and to what, size and checksum.

## The style (fixed; the owner's)

- A one-colour halftone of the photo: round white dots on a 45° grid, about 110 dots across the square, dark tones left transparent so the page's colour shows through as the shadows; contrast lifted a little so the face reads in dots.
- One thin, smooth white outline just outside the head and shoulders, following the hair's overall shape.
- A square crop, head and shoulders, the head near the top, the face filling most of the width, the shoulders running off the bottom; no background at all.
- The likeness is the photo's own: the dots are made by code from its tones, never by an image model; the image model draws only the outline line, which code extracts and lays over the dots.
- One set of settings for every teacher, recorded with each portrait (`recipe_version`, `settings`).
- Output: a 1,000 by 1,000 PNG master, pure white on transparency.

## The pipeline, per teacher

1. Choose the best candidate original not yet set aside: public domain first, then the clearest and largest.
2. Check the original with a vision model: one person, the face fully in view and large enough, not badly damaged. A group photo, a tiny or ruined original is set aside before anything is spent.
3. Cut-out: a background-removal model (Bria RMBG 2.0 or the like; a direct fal key if OpenRouter has none). Keep the cut-out for later tries.
4. Crop, by code. 5. Descreen, by code: detect a printed dot pattern by frequency analysis, filter it, edge-preserving blur, restore contrast; skip when there is none.
6. Halftone, by code, straight onto transparency.
7. Outline: an image model (starting setting Gemini 3 Pro Image; challengers GPT Image 2 and FLUX.2 Pro) draws one white contour around the cut-out on black; code keeps only the line.
8. Check the draft with a vision model of a different family than the outline model: outline hugs the figure, cut-out clean, no moiré, face reads and matches the original, crop matches the examples. A failing draft is remade; a passing one is delivered.
9. Failures: two failures set an original aside; a turn-down from the library (in `status.json`) sets it aside at once; at most three originals per teacher; then the teacher keeps the blank portrait and the tool tries again on a later run when new candidates appear.

## The output: the Drive folder

One shared Google Drive folder the owner gives the tool access to, laid out so the library's Drive door can read it the way it reads library-pipeline's deliveries (hourly; a file is taken only once its manifest row exists):

```
portraits/
  runs/<run-id>/manifest.json        one manifest per run (the contract)
  runs/<run-id>/masters/<teacher_id>.png   1,000 × 1,000 PNG masters, white on transparency
  runs/<run-id>/originals/<teacher_id>.jpg  the original, downsized to at most 1,600 px on the long side,
                                            for the admin's comparison in the queue only (PORT-060)
  runs/<run-id>/report.md             what was done, spent and set aside, in plain words
  requests.json                       written by the library; read by the tool (absent at first)
  status.json                         written by the library; read by the tool (absent at first)
```

- **`manifest.json`** follows `portraits.manifest.schema.json` unchanged: one record per portrait with the teacher (`person_id` carries the `teacher_id` slug; `name`, `born`, `died` as well, so a record stands on its own), the master's file name and SHA-256, the original's source, link, title, creator, date, licence, licence link, credit and how it was matched, the attempt number, the check's notes, any originals set aside and why, and a `request_id` when the draft answers a request. The `tool_run` block records the run id, start time, tool version and the settings used.
- A record whose teacher can't be matched to the list, or whose licence is missing, is never written; the report names it instead.
- A re-delivery for a teacher in a later run replaces the waiting draft; the library handles that by `teacher_id`.
- Nothing goes live from the tool: every portrait lands in the library's approval queue once the library exists. Until then the folder is simply the delivery.
- The **bulk-upload zip** is the same thing in one file (masters plus `manifest.json`), made on request as a fallback for the admin's Imports page.

## Running and limits

- Runs on the owner's PC or any machine with its keys; each teacher is a resumable job in the tool's own queue; a run that stops part-way resumes without redoing paid steps.
- Its own OpenRouter key and a spend cap, $250 for the first run (about 17 cents an attempt is the estimate; the first run for a few hundred teachers $100 to $200; the trial about $30). Stops at the cap. Logs spend per attempt and totals it in the run report.

## The trial, inside the first run

Before the first run over every teacher: the owner's three originals (targets: the hand-made portraits) plus about 20 found originals including scanned prints with a dot pattern, a tiny original, a group photo, an engraving and a damaged print; the three outline models each with the same cut-out and code; the check scores them, the best wins, the cheaper when close; a board of every result beside its original and the examples goes to the owner for a veto; nothing waits for the owner.

## Done when (against the contract, not the library)

- `teachers.csv` with the owner's list loads; a row with a bad slug or an impossible date is refused with the row named.
- A run writes a complete `runs/<run-id>/` to the Drive folder, and its `manifest.json` validates against the schema (the repo's `validate.py` or the same check in the tool); a record with no licence is refused naming the field.
- A small receiver stub in the tool's repo, enforcing the manifest schema over fixtures of teachers, requests and statuses, accepts the run; `requests.json` and `status.json` fixtures change what the next run does (a request first, an approved teacher skipped, a turned-down original set aside).
- The owner's three examples are reproduced by the pipeline closely enough that the check passes them against the hand-made targets.
- The trial's board exists, the defaults are set from it, and one full harness run (plan, build, tests, digest, veto) has completed on this project.
- Nothing in the tool reads the library's reference shelf or its scans; originals come only from the two sources by the three match rules.

## What the library will build on its side (not this project)

So the two projects agree, the library's build (Library-AI---Rev1) will: read `portraits/runs/*/manifest.json` from the Drive folder through its Drive door and make a queue item per record, with the master and the original beside it (PORT-060, PORT-090); adopt `teacher_id` as the people record's id or alias; write `requests.json` and `status.json` back to the folder from the queue's decisions and the people screen (PORT-061); keep the bulk-upload zip as the manual fallback; build the credits page from the manifest's records (PORT-031, PORT-032); show readers only approved portraits or the blank one (PORT-050). The library's acceptance check of this hand-off is importing this tool's sample run unchanged. The tool doesn't choose which teachers exist beyond the list, doesn't edit the library's records, and never serves images to readers.
